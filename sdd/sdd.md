## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий SDD описывает, **как** будет устроена desktop-версия «Рецептус» 0.1: слои, модули, хранение данных и ключевые алгоритмы. Документ опирается на согласованный SRS (`srs/srs.md`) и адресован разработчику, архитектору и заказчику при согласовании плана работ.

Связанные документы: SRS 0.1, ADR в `docs/decisions/`, план итераций в `docs/plans/`.

### 1.2 Область применения {#12-subject-scope}

Проектируется локальное приложение «Рецептус» 0.1 для одного холодильника и одного пользователя на Windows: учёт продуктов, контроль сроков, подбор рецептов из стартового набора, список недостающих ингредиентов, поиск, сохранение в локальных файлах. Свои категории и рецепты пользователя проектируются заранее (модель данных их допускает), но реализуются в версии 0.2.

Вне границ дизайна: сеть, СУБД, авторизация, магазин, ИИ, несколько холодильников, уведомления ОС.

## 2. Обзор дизайна {#2-design-overview}

### 2.1 Задачи стейкхолдеров {#21-stakeholder-concerns}

| Стейкхолдер | Задачи | Как адресуется в SDD |
|-------------|--------|----------------------|
| Заказчик (Ройко А.А.) | Понятные сроки, приоритеты, границы 0.1 | План итераций, приоритеты функций, ADR о границах |
| Пользователь | Простой экран, быстрый подбор рецептов | Представления Interface / Interaction |
| Разработчик | Ясная структура модулей и данных | Composition, Logical, Information |
| Проверяющий | Трассировка к REQ-* | Ссылки на SRS в каждом View |

### 2.2 Выбранные точки зрения {#22-selected-viewpoints}

Для версии 0.1 используются: **Context**, **Composition**, **Logical**, **Information**, **Interface**, **Interaction**, **Algorithm**, **Deployment**. Точки зрения Physical (серверная инфраструктура), Concurrency (многопоточный сервер) и Patterns сверх MVC не разворачиваются — приложение однопользовательское и локальное.

#### 2.2.1 Контекст {#221-context}

Система — «чёрный ящик» на ПК пользователя. Единственный актор — домашний пользователь. Внешних систем нет.

#### 2.2.2 Композиция {#222-composition}

Три слоя: UI (Swing), Domain (учёт и подбор), Persistence (файлы JSON/CSV в каталоге пользователя).

#### 2.2.3 Логическое представление {#223-logical}

Сущности: `Product`, `Category`, `Recipe`, `Ingredient`, сервисы `FridgeService`, `RecipeMatcher`, `StorageService`.

#### 2.2.7 Информация {#227-information}

Данные хранятся в локальных файлах без СУБД (см. ADR-0001).

#### 2.2.8 Интерфейс {#228-interface}

Главный экран и форма продукта по REQ-INT-001 / REQ-INT-002.

#### 2.2.9 Взаимодействие {#229-interaction}

Сценарии: добавить продукт → пересчёт сводки и рецептов; поиск; добавить свой рецепт.

#### 2.2.10 Алгоритм {#2210-algorithm}

Алгоритм совпадения рецепта и ранжирования по скоропортящимся (REQ-FUNC-006).

#### 2.2.14 Развёртывание {#2214-deployment}

Один узел: ПК пользователя с JRE 17+, jar/Maven-сборка.

## 3. Проектные представления {#3-design-views}

### VIEW-001 — Контекст системы

* **ID**: VIEW-001-context
* **Title**: Контекст «Рецептус» 0.1
* **Viewpoint**: Context
* **Representation**: Desktop-приложение на ПК пользователя. Актор — домашний пользователь (клавиатура/мышь). Нет внешних API, СУБД и сетевых сервисов.
* **More Information**: SRS REQ-INT-003, REQ-INT-004; ADR-0001.

```text
[Домашний пользователь] --UI--> [Рецептус 0.1] --файлы--> [Каталог пользователя]
```

### VIEW-002 — Композиция слоёв

* **ID**: VIEW-002-composition
* **Title**: Слои приложения
* **Viewpoint**: Composition
* **Representation**:
  * `ui` — `HomeFrame`, `ProductFormDialog`, таблицы и кнопки Swing;
  * `domain` — модели и сервисы учёта/подбора;
  * `persistence` — чтение/запись файлов продуктов, категорий, рецептов.
* **More Information**: ADR-0002; SRS разделы 3.1–3.2.

### VIEW-003 — Логическая модель

* **ID**: VIEW-003-logical
* **Title**: Основные типы
* **Viewpoint**: Logical
* **Representation**:
  * `Product` — name, categoryId, expiryDate, optional weight+unit;
  * `Category` — id, name (пользовательские);
  * `Recipe` — name, list of Ingredient (name, amount?, unit?);
  * `FridgeService` — CRUD продуктов, сводка, срочные (≤ 3 дней);
  * `RecipeMatcher` — фильтр и ранжирование рецептов;
  * `StorageService` — load/save.
* **More Information**: REQ-FUNC-001…011.

### VIEW-004 — Модель данных в файлах

* **ID**: VIEW-004-information
* **Title**: Локальное хранилище
* **Viewpoint**: Information
* **Representation**: Каталог данных пользователя содержит файлы списка продуктов, категорий и рецептов (стартовый набор + пользовательские). Формат — текстовые структурированные файлы (JSON). СУБД не используется.
* **More Information**: REQ-FUNC-007, REQ-INT-003; ADR-0001.

### VIEW-005 — Пользовательский интерфейс

* **ID**: VIEW-005-interface
* **Title**: Главный экран и форма продукта
* **Viewpoint**: Interface
* **Representation**: Состав блоков совпадает с `приложения/home-page.sysml` / `product-form.sysml` и PNG. Пустые состояния: «В холодильнике пока пусто», «нет срочных списаний», «недостаточно продуктов для рецептов».
* **More Information**: REQ-INT-001, REQ-INT-002, REQ-FUNC-003, REQ-FUNC-005, REQ-FUNC-006.

### VIEW-006 — Сценарий добавления продукта

* **ID**: VIEW-006-interaction-add
* **Title**: Добавление продукта и пересчёт
* **Viewpoint**: Interaction
* **Representation**:
  1. Пользователь нажимает «Добавить продукт».
  2. Открывается форма; ввод и валидация (REQ-FUNC-008).
  3. При «Сохранить» `FridgeService` добавляет продукт.
  4. `StorageService` сохраняет файлы.
  5. UI обновляет список, сводку, срочные и подбор рецептов.
* **More Information**: REQ-FUNC-002, REQ-PERF-001.

### VIEW-007 — Алгоритм подбора рецептов

* **ID**: VIEW-007-recipe-match
* **Title**: Совпадение и приоритет waste
* **Viewpoint**: Algorithm
* **Representation** (псевдокод):
  1. Для каждого рецепта проверить каждый ингредиент: есть продукт с тем же именем (без регистра); если у продукта указан вес — хватает с учётом г/кг и мл/л; если вес не указан — запас считается достаточным.
  2. Оставить только полностью обеспеченные рецепты.
  3. Отсортировать по числу используемых скоропортящихся продуктов (срок ≤ 3 дней) по убыванию.
  4. Если список пуст — показать «недостаточно продуктов для рецептов».
* **More Information**: REQ-FUNC-006; оценка трудоёмкости — см. `docs/plans/priorities.md`.

### VIEW-009 — Список недостающих ингредиентов

* **ID**: VIEW-009-missing-ingredients
* **Title**: Рецепты, которым не хватает одного-двух продуктов
* **Viewpoint**: Algorithm
* **Representation** (псевдокод):
  1. Для каждого рецепта `RecipeMatcher` считает ингредиенты, которых нет в холодильнике или не хватает по количеству.
  2. Если недостающих 1 или 2 — рецепт попадает в список почти подходящих вместе с перечнем недостающего (название, количество, единица).
  3. Рецепты с тремя и более недостающими ингредиентами не показываются.
  4. Если список пуст — показать «нет рецептов, которым не хватает одного-двух продуктов».
  5. Заказ и оплата не выполняются: блок только отображает список.
* **More Information**: REQ-FUNC-012; добавлено во втором раунде с заказчиком (CH-03). Расчёт переиспользует сопоставление из VIEW-007, поэтому вынесен в тот же компонент. Блок UI делает junior, интеграцию и тесты — middle (`docs/plans/iteration-plan-v2.md`).

### VIEW-008 — Развёртывание

* **ID**: VIEW-008-deployment
* **Title**: Узел выполнения
* **Viewpoint**: Deployment
* **Representation**: Один ПК Windows + JRE 17. Сборка Maven. Установка — запуск jar/скрипта без сервера.
* **More Information**: SRS 3.5; ADR-0002.

## 4. Решения {#4-decisions}

Значимые решения вынесены в ADR:

| ID | Title | Файл |
|----|-------|------|
| ADR-0001 | Локальные файлы без СУБД | `docs/decisions/0001-local-files-without-db.md` |

Краткие записи:

* **001-local-files**: выбран вариант файлов в каталоге пользователя, потому что SRS запрещает СУБД и сеть для 0.1.
* **002-swing-layers**: выбран Swing и три слоя UI/Domain/Persistence, потому что стек темы — Java desktop, команда учебная, нужна сопровождаемость без оверинжиниринга.
